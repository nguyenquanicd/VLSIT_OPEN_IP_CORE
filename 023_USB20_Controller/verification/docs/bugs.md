## Triage notes

- BUG-001: the checker was not changed after the failure (R-243). The expected value comes from the bit-serial definition of the standard and reproduces the published token examples and the residual 01100b. The development testbenches in `verification/env/tb` compute CRC5 with the same reversed order as the RTL, which is why their runs passed (the correlated-error risk RISK-003 of the plan). Root cause needs confirmation by a human (R-238).
- CRC16 (`m_usb2_crc16`): properties a_crc16, a_crc16_tx and a_crc16_res pass for one and two bytes per cycle; no finding.
- Runs r0001, r0005, r0007, r0008: environment failures of the runner or the sby file (no design verdict), kept as history.
- Run r0009, property a_ocp_hold: testbench fault. The harness let the `ocur` flag rise without an event, which the CSR cannot do (write-1-to-clear flag set only by the event, section 11.3). An environment assumption was added; the property itself was not changed.
- Run r0013, a_rst_bus_rel: testbench fault. The release property compared a count of past cycles with the current output while the reset input was low again in the same step; the current input was added to the condition. The assertion of reset is checked in the same step.
- Proof depth: a_ocp_trip, a_ocp_hold and the reset properties did not close by induction with this harness (result UNKNOWN in r0011 and r0014) and are reported as bounded proofs of depth 60. The plan asked for unbounded proofs: this is a deviation that needs a helper invariant or the reviewer's acceptance.
- These fixes were made by the AI agent on the user's instruction ("tự fix bug"); each root cause still needs confirmation by a human (R-238).
- Run r0018 (first run of t_dev_enum_bulk_dma): besides BUG-004 the failures were testbench faults: (1) the scenario expected `u2_sts.speed` = full-speed before enumeration, but the field is documented as undefined while detached; (2) it expected no interrupt before the bus reset without a requirement behind it; (3) the partner model left the bus idle in high-speed, so the device correctly went back to the reset check after 3 ms of idle and chirped again. The harness now sends SOF tokens as a high-speed host does. (4) The model assumed that a second transfer starts at the programmed DMA address; the register description says hardware advances the address, so the scenario now checks the advanced value.
- FND-001 (open, specification): an endpoint that exists in the build but was never enabled answers NAK to OUT, IN and PING. REQ-FUNC-001 says a token that does not match an "initialized endpoint" is ignored, and the CSR has no field that marks an endpoint as configured apart from the transfer arm bit. The owner must decide whether a never-enabled endpoint is "initialized"; the test uses a missing endpoint number until then.
- FND-002 (open, specification): `u2_sts.speed` reads 0 (high-speed) before enumeration while its description gives reset value 1; the description also says "undefined while detached". No check is made on it before the enum interrupt.
- Runs r0026 to r0039 of t_fi_bus_errors and the debug scenarios: two testbench faults were found next to BUG-006. (1) The keep-alive SOF of the partner model could be sent between a data packet and its handshake, which a host never does; delays inside a transaction now use an operation without keep-alive. (2) The scenario expected the global `timeout` flag for a lost ACK in device role; the event is reported in the per-endpoint `timeout` flag (ERR-004 names the global flag for the host channel), so the check reads `u2_epi_int`.
- Runs r0041 and r0042: environment failure (tool path order in the runner), no design verdict.
- Run r0053: the harness assertion "write strobes all ones" was a testbench fault; REQ-IF-006 asks for full-width aligned beats (AWSIZE), and partial strobes on the last beat of a short packet protect the bytes after the buffer. The check was removed; the memory compare still proves that only the packet bytes change.
- Run r0055: the scenario expected NAK on the OUT packet that follows an AXI error. With the implemented stop the bus side still accepts packets while the receive region has room; the scenario now checks the stop through an IN endpoint that gets no data, and restarts the DMA through `dma_en`.
- FND-003 (open, design): a read burst that ends with an error response has already written its data rows to the FIFO; the packet is committed and can be sent on the bus. The error is reported and the DMA stops, but the corrupted packet is not discarded.
- FND-004 (open, specification): `u2_hsts.win_en` also enables the FIFO windows of the AXI slave block (`m_usb2_axs`), a second meaning that the field description does not mention.
- BUG-008 and BUG-009 added behavior to the RTL; the exact stop and drop semantics chosen (packet dropped at a window violation, DMA restart through `dma_en`) are not spelled out in the specification and need the owner's confirmation.
- Runs r0073 to r0075 of t_dev_iso_int_mix: testbench faults next to BUG-010 and BUG-011: the keep-alive SOF was off during long waits (the device correctly re-ran the reset check); the expected-packet time-out of the harness was shorter than a 512-byte packet; the interrupt endpoint was armed twice, which queued a second packet.
- FND-005 (open, design): FIFO underflow is never reported (`u2_irq_raw.fifo_udf`, `u2_epi_int.unf`); the device engine ties the event to 0.
- Runs r0096 to r0107 of t_dev_suspend_lpm_reset: testbench faults next to BUG-013 to BUG-018: the idle time was measured from the wrong point (the scenario now sends a last SOF and measures from it); the scenario expected the suspend within 875 us of the reversion, but REQ-FUNC-018 puts only the line sample in that window and the suspend current within 10 ms; the keep-alive restarted too late after a short idle; the partner model did not show J after an L1 entry; the LPM status was read before the status word had crossed; a bLinkState other than L1 was expected to get no answer, the LPM ECN requires STALL.
- Runs r0131 to r0133 of t_dir_test_mode: testbench faults: the packet queue was flushed before the reset instead of after it, and the pin check of the harness had no group for TXValid.
- Run r0140 and r0141 of the performance scenario: testbench faults. With TSCALE = 256 a real 125 us microframe is longer than the scaled idle timer, so the scenario runs on the TSCALE = 1 build; and the scenario re-armed the endpoint before the CSR showed the end of the previous transfer. FND-006 (open, specification): a write of `ep_en` = 1 while the bit still reads 1 (the hardware clear has not crossed yet) starts no DMA job and gives no error; the driver rule "wait for `done` before re-arming" is not stated in section 11.2.
- Run r0136 of the reset scenario: testbench fault, the AXI memory model was not reset together with the DUT.
- t_fml_fifo (runs r0213 to r0219): the transmit-queue invariant (count never above the region size) is proved by bounded model checking to depth 28 under the reviewed assumptions listed in `tb/formal/fifo/fml_fifo.sv` (r0219 task fifo_tx). The receive-queue invariant is NOT established (task fifo_rx fails in r0218 and r0219): the counterexample pops a received packet whose second row is not committed yet, i.e. the harness lets the bus port pop before it has read all rows of the head packet, and its model of the packet-port chunks (`rxw_n`, `rxw_b`, `rxw_len`) is a guess from the port names. FND-008 (open): the receive-queue proof needs the exact chunk and commit-latency contract of the packet port in the specification, and a constraint that a POP follows the reads of all rows of the head packet; until then this obligation is not met. The invariant for the free rows of the receive region is in the same task and is not established either.
- Run r0211 to r0212 of t_dir_param_builds: all nine configurations elaborate, the thirteen parameter checks agree with section 8. FND-007 (open, design): REQ-PARAM-004 requires the FIFO depth to be at least the sum of the minimum regions (maximum packet size x (1 + dbuf) x mult per endpoint plus 256 words); `m_usb2_cfgchk` only checks the range 256 to 32768 and a power of two, so a depth that is too small for the endpoint count is not reported.
- t_fml_cdc_xreg is a seeded random unit simulation of `m_usb2_xreg` (`tb/xreg/tb_xreg.sv`), not a formal proof: whole-word, in-order, exactly-once delivery of accepted writes, drop and flag at `xq_free` = 0, `xq_free` range, and event sets from CLK-PHY reaching CLK-BUS. No multi-clock formal engine is available in this environment, so the bounded formal obligations a_xreg_word, a_xreg_tag and a_xreg_free of the plan are covered only by this simulation; the stale-tag rule (REQ-REG-003) crosses the CSR integration and is covered by the device scenarios, not by this test.
- Host scenarios (runs r0250 to r0260): testbench faults: the harness set SE0 before the host drove it (the host takes SE0 seen before its own reset phase as a disconnect), polls were used for waits of milliseconds, and the SOF check expected 125 us at TSCALE = 16. FND-009 (open, design and specification): with PARA_USB2_TSCALE > 1 the host divides the microframe length and also the transaction time estimate of its frame budget (`rtl/m_usb2_host.sv` w_est), so a transaction can overrun the next SOF and the SOF interval varies by +-6 percent (7.38 to 8.25 us instead of 7.81 us at TSCALE = 16). REQ-VER-002 only names the timers of the speed and power controller. SOF accuracy (REQ-FUNC-010) and the frame guard (REQ-FUNC-015) can only be judged at TSCALE = 1; a host run at TSCALE = 1 takes about 3 minutes per bring-up and is part of t_dir_timing_ts1.
- Runs r0263 to r0266 of t_fi_host_bus_errors: testbench faults next to BUG-025 and BUG-026: ERR-004 allows `timeout` or `xact_err` for a lost response (the RTL sets `timeout`; the scenario was changed to accept it); after a corrupted IN packet the host asks again at once, the scenario expected silence; the error flag of a recovered CRC error stays set, as ERR-002 says. FND-010 (open, specification): ERR-004 and ERR-002 do not say which of `timeout` and `xact_err` a lost response sets, and how many retries precede the halt; the scenario used three.
- BUG-028 (fixed, hardening) and a testbench finding, t_fi_ulpi_abort (runs r0302 to r0310).
