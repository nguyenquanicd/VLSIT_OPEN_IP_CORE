# Review of the FTEL/FPT GPIO IP: hardware design specification v2.4 and RTL (GPIO.zip)

Date: 2026-11-21. Review only: **the specification, the zip and the RTL were not changed.**
Reviewed: `FTEL_CDC_IP_GPIO_Hardware_Design_Specification_v2.4.pdf` (23 pages, text and block diagram read) and `GPIO.zip` (6 files: `m_fpt_gpio_wrap.sv`, `m_fpt_gpio_csr.sv`, `m_fpt_gpio_misc.sv`, `m_fpt_gpio_int.sv`, two library cells). The zip was extracted into a scratch folder; the DOCX twin of the PDF was not read.

## 2. Summary

The IP is a small 8-pin APB4 GPIO with a per-pin filtered edge/level interrupt and a per-pin 32-bit edge counter. Its **spec and the sampled RTL behaviour agree on everything that was exercised** (APB timing, strobes, W1C, level-interrupt rule, injection order, filter, latency). The review nevertheless finds problems in four places: the delivered RTL does not compile cleanly (G1), the document set is inconsistent in naming, version and dates (G2, G3), the event path has a reset-domain hazard that was reproduced in simulation (V1) and several design choices are weak for a reusable SoC IP (section 5). The spec lists DMA as unsupported and the RTL has no DMA hook; section 7 gives a minimal design for it.

## 4. Verified by simulation, and one reproduced hazard

All measurements use OSC = 50 MHz and PCLK = 100 MHz (a 2:1 ratio chosen for the test; the spec leaves the ratio open).

| ID | Spec statement | Result |
|---|---|---|
| T1 | One wait state per access; PSTRB lanes; unaligned and unmapped addresses read 0 | As specified (PREADY low for 1 cycle; lane-1 write did not change bits [7:0]) |
| T2 | A pad already high at reset release gives a rising event | RAW_INT[0] set, INT_STA and `o_gpio_int` stay 0 with INT_EN = 0 |
| T3 | Pulses shorter than about 2 OSC cycles are removed | 1 OSC cycle: not counted; 2, 3, 4 cycles: counted once; a 1 PCLK pulse: not counted |
| T4 | Level mode: hardware set wins over the software clear | Clear is lost while the level is active, works after the pad is released |
| T7 | Latency 4 OSC + 3 PCLK (+1 for the output flop) | 12 PCLK cycles at the 2:1 ratio, as expected |
| T8 | INT_INJ must be cleared before RAW_INT | Confirmed |
| T9 | `SYNC_EN` selects 3 or 1 PCLK stage | 4 and 2 cycles by my counting (same difference of 2 stages) |

**V1 (Medium to high). A reset of the OSC domain alone creates false edges.** With a steady high pad and counting enabled for rising edges on pin 6 and falling edges on pin 7, a 3-cycle assertion of `i_gpio_osc_clk_rst_n` (the PCLK domain not reset) produced **1 rising and 1 falling count** after the release. Cause: `reg_event_in` is reset to 0 asynchronously, the PCLK-domain synchronizer sees 1 then 0 then 1 and generates a falling and a rising event (`m_fpt_gpio_misc.sv:98-104, 124-126`). The spec describes only the case "all resets together". Any SoC that resets or restarts the OSC clock domain separately (low-power exit, clock switch) will get false interrupts and false counts. Fix options: tie the OSC reset to the PCLK reset, or hold the event path off (event-valid flag, set after N cycles, cleared by the OSC reset, crossing as a level).

**V2 (Low, by construction, not reproduced).** Counter clear versus count in the same cycle: the count wins and the clear is lost (spec 6.6, code `m_fpt_gpio_csr.sv:767-768` pattern). 400 clears against an event every 14 PCLK cycles did not hit it; it is a rare race and it makes "write 0xFFFF_FFFF to clear" unreliable under event traffic. A clear-wins rule that still counts the event as 1 after the clear, or a read-and-clear register, avoids this.

## 5. Design weaknesses (not defects against the spec)

| # | Finding | Why it matters |
|---|---|---|
| D1 | **`GPIO_CTL.SYNC_EN` resets to 0**, so by default `GPIO_IN` samples the asynchronous pad with a single flop (`m_fpt_gpio_misc.sv:73-75`). | The unsafe path is the default; firmware that does not set the bit can read a metastable value. A synchronized default, with a direct path as an option, is safer. |
| D2 | **The "wake-up interrupt" is not wake-capable.** `o_gpio_wake_int` is the same OR as `o_gpio_int` ("for simplicity", `m_fpt_gpio_int.sv:8`) and both come from PCLK-domain flops (RAW_INT, E0/E1). Only the filter runs on the OSC clock. | If PCLK is gated, nothing can raise the output. The spec says no clock gating exists, so the wake function has no real meaning; either define it (OSC-domain wake request) or remove the port. |
| D3 | **Event rate limits are undefined.** The filter needs about 2 OSC cycles; the PCLK synchronizer needs about 2 PCLK cycles; the spec gives neither the clock ratio (TBD) nor a maximum counted edge rate. If OSC is much faster than PCLK, a pulse that passes the filter can be shorter than a PCLK period and be missed (inference, not simulated). | The counter is advertised as a measurement feature; its accuracy depends on this. |
| D4 | **No atomic set, clear or toggle registers** (listed as unsupported). Software must read-modify-write `GPIO_OUT` and `GPIO_OE`. | An interrupt handler and main code touching different pins of one port can corrupt each other. Every commercial GPIO in the comparison below has a set/clear form or a masked write. |
| D5 | **No error response and no access control.** `PSLVERR` is 0, `PPROT` ignored, unmapped writes ignored (spec 3). | Silent failures during bring-up; no way to protect `GPIO_OE` and `GPIO_OUT` from an untrusted master. |
| D6 | **The counters cost most of the IP.** 8 x 32-bit counters with W1C and incrementers: 511 flops, 3311 generic cells in total (Yosys). | For an 8-pin GPIO this is heavy; no overflow flag, no per-pin option to remove them. A parameter to build 0 to 8 counters would help reuse. |
| D7 | **Width fixed at 8; no parameters.** Counters W1C: a partial clear (write 0x1 to a count of 5) gives 4. | Poor reuse; unusual semantics for a counter. |
| D8 | **The reset default of `INT_MODE` is "rising edge" and a pad high at reset sets RAW_INT** (T2); the spec handles it with a clear step in the init sequence (9.1). | Works, but it is a known cost: every driver must carry the sequence. A pad-state capture at reset release would remove it. |
| D9 | **Output enable polarity and pad control are outside the IP.** No open-drain mode, no pull or drive control, no output-synchronization of `OE`/`OUT` pairs (a write of `OUT` then `OE` is the documented order to avoid a glitch). | Acceptable if the pad wrapper owns them, but the contract is only a TBD in the spec. |
| D10 | **Rule-check result (VLSIT default rules v2): FAIL.** About 110 findings: 31 input ports declared `logic` instead of `input wire`, 21 header fields, 19 name-length findings (ports up to 34 characters), 14 naming-table findings, 8 port-group comments, 6 `wire` declarations, 5 missing `` `timescale ``, a tab-indented wrapper. | Only relevant if the IP is to follow this repository's rules; FPT's own rules were not available. The CSR header claims "follows the VLSIT RTL Design Rule v2" and does not. |

## 6. Comparison with commercial and open GPIO blocks

Sources for the right-hand columns are the reviewer's general knowledge (not verified in this run) and, where marked, the retained documents of the earlier GPIO and DMA research (`research/gpio_dma_feature_research_report.md`).

| Function | This IP | Typical commercial or open GPIO (general knowledge) | Assessment |
|---|---|---|---|
| Pins | 8, fixed | 16 to 32, parameterizable | Narrow |
| Output update | Whole-register RMW | Set/clear/toggle or masked write (STM32 BSRR, RP2040 aliases, BCM2835 GPSET/GPCLR: D1 p19, D3 p90 of the research) | Missing |

| Input filter | Fixed about 2 OSC cycles | Often programmable debounce | Fixed |

| Edge counter | 8 x 32-bit | Rare in a GPIO block (usually a timer capture) | Extra, costly |

| Version register, capability register | Version only | Version plus a pin-count and feature register | Missing capability register |

## 7. DMA support: a minimal design on this structure

The spec (section 3) excludes DMA. Evidence from the earlier research gives four mechanisms; two fit this IP cheaply and one needs a decision.

1. **Mask-guarded DMA write to the output data** (research F1; MSPM0G, p670): add a `GPIO_DMA_MASK` register (8 bits, reset 0) and let the DMA master write `GPIO_OUT` through a bus that already exists (the APB slave). Priority rule: a mask bit set gives the DMA priority, clear gives the APB master. Cost: one register and a per-bit merge. Prerequisite: the system DMA must be able to write APB addresses at the speed it needs.
2. **Set, clear and toggle aliases** (D1 p19, D3 p90): three write-only registers beside `GPIO_OUT` so that a DMA or an interrupt handler changes selected pins without RMW. This also fixes D4.
3. **Pin event to a DMA request** (research F2; TM4C `GPIODMACTL`, MSP430 `DMAE0`): the existing filtered edge pulse `w_gpio_count_event` / `w_gpio_int_event` of each pin could drive a per-pin DMA request (`GPIO_DMA_EN`, per-pin), with a one-cycle pulse or a level request that the DMA acknowledge clears. The event is already in the PCLK domain, so no new crossing is needed; the request must be defined as lost-or-latched when a second edge arrives before the acknowledge (a counter value read already shows the lost-event problem of V2).
4. **Event fabric** (research F3): only useful if the SoC has one; export `w_gpio_int_event` as a one-cycle event output.

Verification for any of these: the T-series in `review/tb/tb_gpio.sv` extended with a DMA model (back-to-back writes at the PCLK rate, a write colliding with an APB write to the same bit, a request with and without acknowledge). Patent possibly relevant (research section 9, US 8,943,238 and US 10,515,036, claims not read): legal review is needed before reuse of the DMA-mask idea.

## 8. Recommended order of work

1. G1: fix the CSR/library mismatch (remove the async branch for this release, or ship the matching synchronizer). Re-run lint in every tool of the flow.
2. G2, G3: one name and one version across spec, RTL, `GPIO_VERSION` and the signoff define; confirm the reset pin polarity of the signoff cell.
3. V1: decide the reset rule of the OSC domain and add it to the spec (and a test).
4. D1, D2: change the `SYNC_EN` default; define or remove `o_gpio_wake_int`.
5. D3: fix the clock ratio and the maximum event rate in the spec; derive a minimum pulse width.
6. D4 and the DMA items of section 7 if the SoC needs them.
7. Complete the spec: section 10 (use the T-series as a start), section 12 (SDC: the two clocks as asynchronous groups, the CDC paths of the three synchronizers per pin, input delay on `i_gpio_pad_in`), acronyms, the table of contents.
